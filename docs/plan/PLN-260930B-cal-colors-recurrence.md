# Calendar Colors and Recurrence Plan (색상·반복 일정 구현 계획)

## 1. Scope (범위)

[요구사항 분석](../analysis/REQ-260930B-cal-colors-recurrence.md)을 기준으로 `frontend-acm`과 PostgreSQL `ACM_DS` 백엔드를 수정한다. 2026-09-30 사용자 “진행” 승인 후 구현 및 로컬 검증을 완료했다. 운영 배포는 아직 하지 않았다.

## 3. Data and API (데이터·API 설계)

### 3.1 Color settings (색상 설정)

- 신규 `amb_acm_cal_color_setting`: UUID PK, `ent_id`, 기준 `CATEGORY|ASSIGNEE`, category key 또는 teacher UUID, palette key, timestamps. 테넌트+기준+대상 유일 제약 및 대상 타입 CHECK를 둔다.
- `GET /api/acm/cal/color-settings`, 관리자 `PUT /api/acm/cal/color-settings`를 추가한다. 담당자 존재·소속과 팔레트 키를 검증하며 변경 목록을 한 트랜잭션으로 저장한다.
- 팔레트 키에서 배경·테두리·글자색을 함께 결정하는 공통 resolver를 사용한다. 미설정은 기존 카테고리 기본값 또는 담당자 기본색으로 처리한다.
- 사용자·학원별 표시 기준을 저장한다. 서버에는 학원 공통 색상만 저장하고 클라이언트 표시 기준 캐시 키에 사용자·학원 식별자를 포함한다.

### 3.2 Manual recurrence (직접 등록 반복)

- 신규 `amb_acm_cal_recurrence_series`: 테넌트, 작성자, 시간대, 시작 현지시각, 기간, 검증된 규칙, 종료 조건, 일정 템플릿, 생성 커서, 중단·버전 정보.
- 신규 `amb_acm_cal_recurrence_occurrence`: 테넌트, series FK, 원래 회차 키, event FK, 예외 상태. `(ent_id, series_id, occurrence_key)`와 event 연결에 유일 제약을 둔다. 이동 후에도 원래 회차 키를 유지한다.
- 수동 반복과 ICS 원본 저장 모델은 구분한다. 기존 검증된 반복 계산 기능은 공통 순수 함수로 추출·재사용하고 기존 ICS 원본을 재작성하지 않는다.
- 반복 DTO는 종류별 discriminated input으로 설계한다. 일/주/월은 RRULE로 표현하고 특정일자는 날짜 목록으로 표현한다. 양의 간격·횟수, 유효 날짜·시간대, 주요일 최소 1개, 실제 회차 존재 여부를 검증한다.
- 제안 API: `POST /api/acm/cal/recurrence/preview`, `POST /api/acm/cal/recurrence/series`, `POST /api/acm/cal/recurrence/events/:id/{impact|update|delete}` (scope + version; 기준 회차는 event ID로 조회). 기존 단일 일정 API와 DTO의 기본 동작은 유지한다.
- 미리보기와 저장·연장에 같은 계산기를 사용한다. 무기한은 최초 선행 1년 및 조회 구간을 생성하고 일일 연장 작업을 추가한다. 큰 유한 범위도 작업량을 제한하여 분할 처리하며 저장된 규칙을 임의로 잘라내지 않는다.
- 테넌트·시리즈 단위 잠금, 생성 요청 idempotency key, 버전 충돌 감지로 재시도·동시 편집을 보호한다. 일부 생성 실패는 성공으로 표시하지 않으며 재시도 가능한 상태를 남긴다.
- 이후 수정은 원래 회차 키를 기준으로 적용 시작점과 변경 이력을 저장한다(`crs_changes`). 이후 삭제는 원래 규칙의 cutoff로 처리한다. 전체 변경은 회차 예외와 연결 이력 보호 정책을 적용한다. 삭제 예외는 자동 연장으로 복구하지 않는다.

### 3.3 Existing business rules (기존 업무 규칙)

- 현재 `CalEventService.createLocked`는 저장 후 보다 대기실·초대 알림을 처리하므로 단순 반복 호출하지 않는다. 시간·권한·화상 설정·담당자·초대자 검증과 이벤트/초대자 저장을 재사용 가능한 내부 로직으로 분리한다.
- 이벤트·회차 매핑·초대자 저장은 트랜잭션으로 묶고 알림은 커밋 이후 멱등 처리한다. 반복 등록 초대 알림은 시리즈 요약 1회로 묶고 자동 연장은 신규 초대 발송 대상으로 취급하지 않는다.
- Google Meet 입력 링크는 기본적으로 각 회차에 공유한다. Google Meet 링크 자동 발급 기능은 범위 밖이다. BODA는 기존 회차별 대기실·입장 방식을 유지하며 생성 재시도로 방이 중복되지 않도록 한다.
- 모든 조회·수정에 기존 테넌트 및 역할 권한을 적용한다. 직접 등록한 반복 기능이 기존 일정 조회 범위를 넓히지 않도록 한다.
- 수업·출결·피드백·상담 연결을 조사해 보호 조건을 명시적으로 구현한다. 연결된 이력에 대한 일괄 소급 변경은 수행하지 않는다.
- 기존 ICS 원본·수정 회차·중단 상태를 보존한다. ICS의 무기한 연장과 새 수동 반복 연장은 독립적으로 실행한다.

## 4. Work Sequence (작업 순서)

1. 사용자 계획 확인 후 최신 main 기반 격리 작업 공간에서 구현한다. 기존 작업 디렉터리의 변경은 유지한다.
2. 색상 테이블/API, 색상 resolver, 설정 모달, 네 가지 보기 및 범례 적용.
3. 수동 반복 모델·계산기·미리보기·생성·연장 및 기존 생성 서비스 분리.
4. 반복 입력 폼, 종료 조건, 수정/삭제 범위, 보호 회차 안내, ko/en/vi/zh-CN 번역.
5. 핵심 테스트·빌드, 스테이징 마이그레이션 및 화면 검증, 결과 보고서·스크린샷 작성.
6. 운영 배포는 배포 지시에 따라 진행한다. 마이그레이션은 기존 ICS 1023 이후 충돌 없는 번호를 배정한다.

## 5. Verification (검증)

| 영역 | 필수 확인 |
|---|---|
| 색상 | 저장/복원/새로고침, 모드 전환, 네 가지 보기, 미지정·삭제 강사, 레거시 카테고리, 대비 |
| 반복 계산 | 일 N간격+주말 제외, 주 복수 요일, 29/30/31일·윤년, 종료 포함 날짜·횟수, 특정일 중복, 시작일 제외 |
| 시간 | Asia/Seoul 및 DST 지역, 종일, 자정 넘김, 월 경계 |
| 일관성 | preview=실제 회차, 재시도·동시 요청·연장 중복 방지, 수정/삭제 예외 보존 |
| 권한 | 타 테넌트 대상 거부, 비관리자 색상 변경 거부, 기존 생성/수정 권한 유지 |
| 연계 | Google/BODA 설정, 중복 대기실·알림 방지, 출결·수업 연결 회차 보호 |
| 회귀 | 단일 등록, 기존 필터, ICS EXDATE/이동 예외/무기한 연장/중단 유지 |

단위 테스트는 계산·색상 판정·권한에 집중하고 PG 통합 테스트로 멱등성과 트랜잭션을 확인한다. 실제 화면에서 색상 변경과 평일 반복 미리보기·저장 결과를 캡처한다. 불필요한 운영 테스트 일정을 생성하지 않는다.

## 6. Release and Recovery (배포·복구)

추가형 마이그레이션 → 백엔드 → 프론트엔드 순으로 배포한다. 배포 전 DB 백업을 확보한다. 문제 발생 시 신규 반복 등록·연장 작업을 중지하고 원인 범위의 시리즈만 식별한다. 기존 단일·ICS 데이터를 유지하며 코드 롤백 시 신규 테이블과 생성된 업무 데이터는 자동 삭제하지 않는다.
