# Student List Improvement Plan (학생관리 목록 기능개선 계획)

## 1. Outcome and Scope (목표와 범위)

[요구사항 분석서](../analysis/REQ-260918-std-site-list-improvement.md)를 기준으로 `/admin/std`에서 **TPI / Trinity Academy / Santa Croce별 학생을 구분하고, 학생별 수업 시작일과 담당강사를 정확히 조회**한다. 엑셀 현재 등록 시트는 TPI 33명, Trinity Academy 3명, Santa Croce 14명의 이름 행으로 구성되어 있다. 이 수치는 원본 분석 결과이며 운영 반영 후 목표 인원으로 강제하지 않는다.

진행 승인 후 사이트 목록·관리와 검토형 업로드의 핵심 구현 및 운영 배포를 완료했다. 후속 사용자 승인에 따라 기존 50명의 소속 사이트만 반영했으며, 다른 학생 필드는 유지했다. 나머지 엑셀 필드 입력은 별도 검토 대상이다. 구현 범위와 운영 검증 결과는 [구현 보고서](../report/RPT-260918-std-site-list-improvement.md)를 참조한다.

## 2. Screen Layout (화면 구성안)

### 2.1 List (기본 목록)

```text

[통합 n] [TPI n] [Trinity Academy n] [Santa Croce n] [미분류 n]

[이름·영문명·학교 검색                       ] [상태: 재원 ▾]
[학교 ▾] [학년 ▾] [담당강사 ▾] [수업 시작일: 시작 ~ 종료] [초기화]

검색 결과 n명                  [선택 n명 · 사이트 변경] [표시 열 ▾]*
┌──┬─────────┬───────────┬───────────┬────────┬────┬──────────┬──────────┐
│선택│ 사이트  │ 이름/영문명│ 학교·학년 │ 담당강사│ 상태│수업 시작일│시스템 등록일│
├──┼─────────┼───────────┼───────────┼────────┼────┼──────────┼──────────┤
│ □ │ TPI     │ 예시 학생A │ 학교 / G8 │ 강사A +1│재원│YYYY-MM-DD│YYYY-MM-DD│

└──┴─────────┴───────────┴───────────┴────────┴────┴──────────┴──────────┘
```

- `n`은 API가 반환한 실제 인원이다. 상태·검색 등 비사이트 필터를 적용한 후 사이트별로 집계한다. 사이트 탭 선택은 다른 탭의 카운트를 0으로 만들지 않는다.
- 기본값은 통합 / 재원 / 등록일 내림차순이다. 사이트는 색상과 텍스트를 함께 표시하고 전체 이름을 확인할 수 있게 한다.
- 이름 클릭은 기존 상세 화면으로 이동하며 목록 URL을 보존한다. 기존 성별 열은 선택 열로 이동한다. 수업 시작일이 없으면 `—`로 표시한다.
- 작은 화면은 탭·표 가로 스크롤을 지원하고 이름·사이트를 우선 노출한다. 긴 강사 이름은 첫 강사와 추가 인원 수로 요약한다.
- 행 선택은 현재 페이지에서만 시작한다. 필터/페이지가 변경되면 선택을 해제하고, 전체 검색 결과 일괄 선택은 초기 범위에서 제외한다.
- 사이트 변경 대화상자는 선택 인원·이전 사이트·새 사이트·변경 사유를 표시한다. 미리보기 이후 데이터가 변경되었으면 재검토한다.

## 3. Data and API Design (데이터·API 설계안)

### 3.1 Site Storage (소속 저장)

제안 기본안은 학생당 현재 주 소속 1개다. 동시 복수 사이트 등록 여부를 먼저 확정한다. 복수 소속이 필요하면 아래 단일 컬럼안 대신 학생-사이트 관계, 사이트별 상태·시작일, 통합 중복 제거 집계를 설계한다.

단일 소속안에서는 `amb_acm_std_student.std_site`를 nullable 문자열과 CHECK 제약으로 추가한다. 허용 코드는 `TPI`, `TRINITY`, `SANTACROCE`; NULL은 기존 미분류다. 기존 학생에 기본 사이트를 일괄 채우지 않는다. `ent_id`·사이트·상태를 사용하는 삭제 제외 인덱스는 실제 조회 계획으로 결정한다. 감사 이력은 기존 감사 저장 방식을 먼저 확인하여 재사용한다.

소속은 상담 유입, 방문자 수, 마케팅 비용의 사이트와 별개 필드다. 이번 변경으로 대시보드의 과거 집계 귀속을 바꾸지 않는다. 복수 강사는 기존 `amb_acm_std_student_teacher`와 등록 서비스를 재사용한다.

### 3.2 List Contract (목록 계약)

기존 `/api/acm/std/students`에 `site`, `teacherId`, `startDateFrom`, `startDateTo` 필터를 추가한다. 기존 검색/상태/학교/학년/페이지 파라미터는 호환한다. 사이트 미지정 필터용 `UNASSIGNED`는 API 값이며 DB에 저장하지 않는다.

- 목록 응답에 사이트와 기존 수업 시작일을 포함한다. 페이지 정보와 사이트별 카운트를 함께 반환하거나 동일 필터를 공유하는 집계 API로 제공한다. 최종 응답 구조는 기존 응답 래퍼를 유지한다.
- `siteCounts`는 선택 사이트 조건만 제외한 공통 필터로 계산한다. `total`은 선택 사이트를 포함한 결과 건수다.
- 담당강사 검색은 관계 테이블의 ID를 사용하고 학생 중복 행이 생기지 않도록 EXISTS 또는 동등한 방식을 쓴다.
- 정렬 필드는 허용 목록으로 제한하고 학생 ID를 보조 정렬로 추가한다. 날짜 NULL 정렬 위치를 고정한다.
- 페이지 크기는 25/50/100으로 제한한다. 페이지 범위 초과 시 마지막 유효 페이지 또는 첫 페이지로 일관되게 보정한다.
- 모든 읽기/변경/집계에 tenant와 삭제 제외 조건을 공통 적용한다. 일괄 변경은 제한된 학생 ID 목록에 대해 권한과 현재 상태를 다시 확인한다.

### 3.3 Import Contract (업로드 계약)

현재 업로드를 즉시 대체하지 않고 기존 템플릿과 새 3사이트 형식을 명시적으로 구분한다. 형식 판별에 실패하면 저장하지 않는다. 제안 API는 `import/preview`와 `import/commit`으로 분리하고 기존 경로와의 호환을 구현 때 확정한다.

미리보기는 서버에 파일 해시·행 위치·학생 후보·변경안·유효기간을 연결한 식별자로 보관한다. 적용 요청은 그 식별자와 사용자의 확정 매핑만 받으며, 클라이언트의 미검증 변경안을 그대로 저장하지 않는다. 적용 직전 대상 학생의 `updated_at`과 권한을 재검증한다. 파일/행 재처리에는 이전 확정 매핑과 실행 기록을 사용한다.

학생 기본값·강사 관계·적용 기록은 하나의 일관된 트랜잭션 단위로 저장한다. 포털 계정 생성·알림·수업 생성 등 부수 효과는 임포트에서 자동 발생하지 않도록 기존 서비스 호출 경로를 검토한다. 원본 파일과 임시 개인정보의 보관기간·삭제 절차도 함께 정한다.

## 4. Work Breakdown (단계별 작업)

| 단계 | 작업 | 산출물·완료 조건 | 관련 요구사항 |
|---|---|---|---|
| 0. 결정·기준 확인 | 단일/복수 소속, 사이트 변경 역할, 운영 명부 기준일 결정. 최신 배포와 소스 재대조 | 확정 설계 및 대사 담당자. 원본 50명과 운영 인원의 차이를 개별 검토할 기준 확보 | S02, S10 |
| 1. 저장·조회 | 확장 마이그레이션, 엔티티/DTO/서비스, 카운트·필터·정렬·페이지, 감사 이력 | 기존 NULL 학생 호환, 동일 tenant에서 사이트별 정확한 목록/집계 | S01–S06 |
| 2. 관리 화면 | 탭·열·필터·페이지, URL 상태, 등록/수정/상담 전환 사이트, 일괄 변경 미리보기 | 데스크톱/작은 화면 검증, 상세 복귀 상태 보존, 4개 언어 | S01–S07 |
| 3. 검증 업로더 | 시트/헤더 파서, 병합 경계, 날짜/학년 원문, 학생·강사 매칭, 미리보기·적용 분리 | 새 파일 33/3/14개 이름 앵커 인식, 보류 행 저장 차단, 재실행 중복 없음 | S08–S11 |
| 4. 운영 대사·반영 | 최신 명부와 원본 개별 매칭, 변경안 확정, 백업, 검토 완료분 입력 | 사이트별 변경 결과와 제외 목록 확인. 미해결 학생은 미분류 유지 | S07–S11 |
| 5. 후속 보강 | 선택 열, 상세 수업 정보, 필터 전체 내보내기, 종료·상담 이력 설계 | 개인정보 노출 범위와 이력 충돌 규칙 검증 | S12–S14 |

1차 릴리스는 단계 1–2로 사이트 관리와 50명 초과 목록 접근을 먼저 제공할 수 있다. 단계 3 검증 완료 전에는 이 원본의 운영 업로드를 진행하지 않는다. 단계 4는 실제 변경안 검토가 끝난 후의 별도 운영 작업이다.

예상 변경 위치:

- `frontend-acm/src/modules/std/`: 목록·필터·표·폼·API 타입/훅 및 업로드 UI.
- `backend/src/modules/acm-std/`: 엔티티·DTO·학생 서비스·임포트 서비스·컨트롤러.
- `backend/src/modules/acm-csl/`: 상담에서 학생 등록/연결 시 사이트 전달과 기존 소속 보존.
- `sql/acm/`: 최신 번호 체계를 확인한 후 확장 마이그레이션 추가.
- 번역 리소스와 기존 감사/권한 모듈: 실제 구조를 확인하여 최소 확장.

| 미리보기 후 운영 학생 수정 | 충돌 감지 후 재검토, 최신 값 덮어쓰기 방지 |
| 미리보기 취소·오류 행 | 학생/강사 관계에 쓰기 없음 |
| 원본 빈 셀·원본에 없는 학생 | 기존 값 보존, 삭제·퇴원 없음 |
| 권한 없는 일괄 변경·내보내기 | 서버 거부, UI 숨김만으로 통제하지 않음 |

파서 테스트는 비식별 합성 워크북으로 작성한다. 실제 원본은 검증 실행에만 사용하고 저장소에 커밋하지 않는다. 적절한 백엔드 단위/통합 테스트, 프론트 타입검사·빌드, 목록과 업로드의 핵심 브라우저 흐름을 검증한다.

## 6. Release and Recovery (배포·복구 계획)

nullable 컬럼을 먼저 추가하는 확장 방식으로 배포하고 기존 API/화면의 호환성을 확인한다. 검증된 백엔드 다음 프론트엔드를 배포한다. 임포트는 기능 배포와 실제 데이터 적용을 분리한다.

데이터 반영 전 변경 대상의 이전 값·관계·실행 식별자를 제한된 저장소에 백업한다. 실패 시 실행별 적용 내역을 기준으로 복구하며, 그 이후 사용자가 수정한 학생은 자동 역변경하지 않는다. 애플리케이션 롤백 시 추가 컬럼을 즉시 삭제하지 않는다. 적용 결과는 신규/수정/동일/보류 건수와 사이트별 집계로 보고한다.
