# Withdrawn Student Implementation Plan (퇴원생 등록·보완 작업계획)

## 1. Scope and Gate (범위와 진행 조건)

[요구사항 분석서](../analysis/REQ-260920-std-withdrawn-import.md)의 67명·48열 매핑을 구현한다. 운영 예비 대조는 기존 이름 후보 51명(재원 8·휴원 4·퇴원 39), 이름 후보 없음 16명이며 최종 등록 건수는 미리보기 검토로 확정한다.

사용자 요청에 따라 화면구성도를 필수로 포함한다. 2026-09-20 “작업 진행” 승인에 따라 구현 중이다. 기존 학생의 현재 상태 적용 방식은 별도 질문 답변을 반영한다. 신규 학생 WITHDRAWN 등록은 명확한 요청 범위이다.

이 추가 도식의 `입력필요` 규칙은 앞선 상세 도식의 개별 빈 값/대시 표시보다 우선한다. 목록의 대시 표시를 바꾸는 요청은 아니므로 목록 표현은 유지한다.

- `std-detail-page.tsx`의 공통 Section과 별도로 작성된 포털 계정·학부모 박스 제목을 함께 수정한다. 기본 12px 제목은 13px로, 굵기는 700으로 통일한다. 제목 외 항목/값의 글자 크기는 변경하지 않는다.
- 공통 InfoRow를 사용하는 다른 화면에 의도치 않게 적용하지 않도록 학생 상세 전용 옵션 또는 래퍼로 `항목 : 값`과 미입력 표시를 제공한다. MAP 메모·목표·특이사항·부모 연락처 등 직접 출력하는 값에도 동일 판정을 적용한다.
- 미입력 판정은 NULL/undefined/빈 문자열/공백 문자열로 한정한다. 0, false, 미분류·미발급 등 유효한 값은 유지한다. placeholder는 표시 계층에서만 처리한다.
- 모바일은 한 열로 배치하며 `항목 : 값` 관계를 유지한다. 긴 항목/값은 자연스럽게 줄바꿈하고, dl/dt/dd 등 접근성 의미 구조를 유지한다.
- 검증: 지정 학생 상세에서 제목 크기·굵기 및 MAP/수업/메모 미입력 표시 확인, 0/false 표시 보존, 긴 값·모바일 줄바꿈, 타 화면 공통 컴포넌트 영향 없음, DB 값 변경 없음.

## 3. Data Design (데이터 설계)

- 기존 `amb_acm_std_student`의 공통 필드는 재사용한다. 입학일·출결번호·닉네임·상세 주소·반·학적/분류 필드는 nullable 신규 필드로 추가한다. 기존 데이터는 NULL로 시작한다.
- 퇴원 이력은 학생 UUID를 참조하는 `amb_acm_std_status_history` 제안 테이블에 source namespace, 원본번호, 원본 상태, 유효일, 사유, 출처를 저장한다. 실제 ACM 상태 전이와 과거 원본 이력은 event type으로 구분한다. 모든 테이블에 ent_id 및 created_at/updated_at을 둔다.
- 원본 식별은 `amb_acm_std_external_identity` 제안 테이블의 `(ent_id, source_system, external_id)` 유일 제약으로 보장한다. 기존 파일해시+행 키 임포트 기록은 실행 이력에 재사용하고, 원본번호는 행 정렬에 독립적인 식별에 사용한다.
- 기존 source identity가 없을 때는 후보만 제시하며 학생 ID 연결을 확정한 후 키를 저장한다. 학생 이름이 이후 변경되어도 확정된 연결을 따른다. 파일명만으로 출처 시스템을 자동 동일시하지 않는다.
- 원본 행정정보는 학생에 연결된 버전 있는 typed JSONB/별도 엔티티로 저장할 수 있다. 허용 키·타입·길이·NULL/0/false 규칙을 DTO에서 고정하고 자유 JSON 편집을 노출하지 않는다. 48개 열의 실제 매핑은 요구사항 표와 1:1 대조한다.
- 이름 없는 보호자는 별도 student contact 구조로 보관하고, 확인된 parent_id를 선택 연결한다. 부모 마스터의 이름 필수 제약을 우회하는 가짜 이름을 만들지 않는다. 실제 부모/학생 관계는 기존 엔티티를 재사용한다.
- 원본 시각은 시간대 없는 local timestamp와 원문을 보존한다. 출처 시간대가 확인되기 전 UTC 변환을 하지 않는다.
- 새 개인정보 저장 위치에는 프로젝트 암호화·마스킹·접근 제어 규칙을 적용한다. 미리보기 상세는 기존 만료/정리 방식을 따르고, 감사 기록은 필요한 변경 필드에 한정한다.

## 4. Implementation Sequence (구현 순서)

1. **정책 확정**: 계획 승인과 기존 재원/휴원 학생 상태 정책을 기록한다. 과거 사이트 작업의 승인 범위와 섞지 않는다.
2. **파서**: `Sheet0` 이름에만 의존하지 않고 A1:AV1의 48개 헤더를 정규화해 확인한다. `등록일  ` 공백을 처리하며 필수 헤더 중복/누락은 거절한다. 이름 있는 67행을 읽고 날짜/식별번호/금액/표시 플래그를 검증한다.
3. **스키마·API**: 신규 nullable 필드·이력·원본 식별 연결·연락 정보를 추가한다. WITHDRAWN 학생의 이메일/사이트 미입력을 등록·수정에서 허용하고 기존 재원 등록의 필수 요건과 회귀 테스트를 유지한다. 계정 발급과 일반 저장을 분리한다.
4. **대조·미리보기**: 기존 `site-import.service`의 만료·권한·실행 기록을 재사용할 수 있도록 형식별 처리로 분리한다. 현재 사이트 형식은 기존 동작을 유지하고 퇴원 형식에서만 WITHDRAWN 및 추가 데이터 매핑을 적용한다.
5. **학생 화면**: `frontend-acm/src/modules/std` 목록·상세·등록/수정·엑셀 모달을 위 도식대로 확장한다. 4개 언어 번역 및 URL 퇴원일 필터를 적용한다.
6. **검증**: 원본 48열 매핑 누락, 기존 필드 보존, 중복·보류, 보호자 공유 번호, 상태 정책, 재실행을 검증한다. 민감한 원본은 테스트 fixture나 Git에 넣지 않는다.
7. **배포·반영**: CI·스테이징 확인 후 운영 서버 백업, 최신 후보 대조, 승인된 선택 행 반영, 결과 재조회, 재실행 미리보기를 수행한다. 사용자가 확정한 상태 정책과 실제 변경 건수를 결과 보고서에 기록한다.

관련 수정 위치: `backend/src/modules/acm-std/{application,presentation,infrastructure}`, `frontend-acm/src/modules/std/{pages,components,hooks,types.ts}`, 각 언어 `std.json`, `sql/acm/` 신규 마이그레이션. Legacy Next.js 사용자 화면은 수정하지 않는다.

## 7. Implemented Layout and Storage (구현 화면·저장 구조)

기존 상세의 세로 박스 구조를 유지하고, 원본 정보는 기본 인적사항 / 학부모 정보 / 입학·퇴원 / 원본 행정정보 네 영역으로 나눈다. 모바일 1열, 데스크톱 최대 3열이며 각 항목은 레이블과 값으로 표시한다. 일반 수정 화면에는 입학일·퇴원일·사유를 추가한다. 원본 정보의 [수정]은 이력만 변경하고 일반 수정은 현재 정보를 변경한다.

```text
기존 학생 상세 박스 (제목 13px, Bold / 빈 값 입력필요)
└ 입학·퇴원 / 원본 정보                         [수정]
  ├ 기본 인적사항: 학교·반·닉네임·주소·학생 연락처
  ├ 학부모 정보: 원본 연락처·관계·이름·출결알림
  ├ 입학·퇴원: 원본 날짜·재원/휴원 여부·사유·메모
  └ 원본 행정정보: 원본번호·수납 참고·등록일
```

원본 식별과 역사 정보는 `amb_acm_std_withdrawn_record`에 통합한다. 48개 필드는 고정 키·타입 검증을 거친 뒤 AES-GCM으로 암호화하여 저장하며, 원본번호는 테넌트/출처 내 유일하다. 별도의 부모 마스터 생성이나 금융/알림 설정 변경은 발생하지 않는다. 변경 감사도 암호화한다. 일반 목록 날짜 검색용 입학일·퇴원일·사유는 학생 테이블 nullable 필드로 추가한다. 동일 원본번호의 재업로드는 빈 값만 보완하며, 이전 원본 내용을 정정할 때는 상세의 명시적 수정을 사용한다.
