## 2. Screen Layout (화면 구성안)

### 2.1 Teacher (강사)

~~~text
[학원명 · 강사]                         [알림][언어][프로필]
[수업일정] [수강생] [자료실] [채팅] [공지*] [마이페이지]
────────────────────────────────────────────────────────
수업일정                          2026년 11월 [이전][오늘][다음]
[월][주][일][목록]                  [학생 전체][수업종류 전체]
┌ 날짜별 일정 ─────────────────────────────────────────┐
│ 10:00  가학생  정규 · 대면  → 수업 상세                │
│ 14:00  나학생  데모 · 비대면 → 수업 상세               │
└──────────────────────────────────────────────────────┘
모바일: [일정] [수강생] [자료실] [채팅] [더보기]
*공지: 테넌트 강사 공지 설정이 켜진 경우만. 더보기에도 동일 정책.
~~~

### 2.2 Student (학생)

~~~text
[학원명 · 학생]                                  [언어][프로필]
[수업링크] [자료실] [공지*] [마이페이지]
────────────────────────────────────────────────────────
수업링크
[연결된 수업 정보]    [지원하는 수업 입장·상세]
모바일: [수업링크] [자료실] [공지*] [마이]
*공지: 테넌트 학생 공지 설정이 켜진 경우만.
캘린더·수강생관리·채팅은 메뉴와 직접 목록 진입에서 계속 제한.
~~~

### 2.3 Students and Detail (수강생 목록·상세)

~~~text
수강생관리
[내 담당 N명] [전체보기(퇴원 포함) M명]
설명: 두 탭 모두 내 담당 학생 범위
[이름·영문명·학교 검색] [이름순]
[이름 / 학교·학년 / 재원 상태 / 상세 보기] × N

학생 상세: 목록 복귀 → 이름·상태 → 기본 정보 → 학습 목표
          → 내 수업링크 → 상담 기록 → 수업 기록
특이사항은 라벨·값·API 모두 계속 제외.
~~~

자료실은 표/모바일 목록, 채팅은 목록-대화 전환, 내 정보는 680px 계정·기기 알림·보안 구성으로 정리한다. 첨부 목업과 다르게 수정한 부분은 제안서의 채택 판단표에 명시했다.

## 3. Work Packages (단계별 작업)

| 단계 | 변경 영역 | 주요 작업 | 검증 |
| --- | --- | --- | --- |
| 0 기준 확정 | 설계 | 본 개선안의 탐색·폭·명칭·기능 분리 확인 | 역할별 화면·정책 대조 |
| 1 공통 셸 | PortalShell, 공용 토큰·메뉴 | 헤더·사이드바·레일·하단 탐색·더보기, 계정 접근 | 역할×메뉴 설정, 실패·로딩, 직접 URL |
| 2 핵심 화면 | PortalCalendarPage, TeacherStudents | 공통 필터·모바일 일정, 목록 탭·카드·상세 날짜 | 필터 유지·그룹 수업·퇴원생·특이사항 |
| 3 콘텐츠·소통 | PortalMaterialsPage, Talk, MyProfile, Push | 표/목록·채팅 전환·인라인 안내·프로필 | 기존 작성·공유·알림·로그아웃 회귀 |
| 4 선택 확장 | 필요한 API·DTO·쿼리 | 다음 수업 묶음, 전체 결과 검색·정렬·집계 | 테넌트 격리·페이지 일관성·호출 수 |
| 5 검수·배포 준비 | 통합 | 반응형·번역·접근성·성능·권한 점검 | 스테이징 검토 후 별도 배포 절차 |

현재 데이터만으로 가능한 UI 작업을 먼저 수행한다. 신규 API가 필요한 기능은 별도 작업으로 분리하고, 목업의 더미 수치·스위치를 제품에 그대로 넣지 않는다.

## 4. Implementation Boundaries (향후 구현 경계)

- 프런트엔드는 frontend-acm/src에서만 작업한다.
- 기존 usePortalMenus / RequirePortalMenu의 역할·테넌트 정책과 설정 갱신을 재사용한다.
- 새 내비게이션이 화면 권한을 결정하는 유일한 수단이 되지 않게 한다.
- 마이페이지·로그아웃은 노출 설정과 관계없이 접근할 수 있게 한다.
- 다음 수업은 학생별 N회 호출 대신 묶음 조회·캐시를 설계한다.
- 검색·집계가 현재 페이지만 대상으로 오인되지 않게 서버 조회 계약을 정한다.
- 기존 메뉴·날짜·필터 상태는 역할·테넌트가 바뀌면 적절히 분리한다.
- 푸시 구독·닫기 유예·로그아웃 연결 정리 동작을 재작성하지 않고 재사용한다.
- 목업의 고정 높이·샘플 날짜·샘플 이름·미동작 버튼은 운영 구현으로 옮기지 않는다.

## 6. Approval Boundary (검토 범위)

이번 요청은 개선안 작성이므로 구현 승인 질문 없이 검토 가능한 문서와 시안을 제공한다. 실제 애플리케이션 구현으로 진행하는 경우 AGENTS.md §9.2의 “요구사항 분석서 + 작업 계획서 작성 후 반드시 사용자 확인” 절차에 따라 확정 범위를 확인한다. 별도 기능 검토 항목은 기본 UI 범위에 자동 포함하지 않는다.
