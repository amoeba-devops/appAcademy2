# Customer Complaint List Plan (고객불만 목록 구현 계획)

## 1. UI Layout (화면 구성안)

```text
좌측 메뉴                  고객불만                         [불만 등록]
  수업일정                 [시작일 ~ 종료일] [사이트 ▼] [채널 ▼]
  수업통계                 [중요도 ▼] [제목/내용 검색       ] [조회]
▶ 고객불만                 총 N건
  학교관리                 날짜 | 사이트 | 채널 | 중요도 | 제목 | 내용 요약 | 수정일 | 작업
                           10/06  TPI      전화    높음     …      …          …    [상세][수정]
                           [이전]              1 / N              [다음]

상세/수정 창
[고객불만 상세 / 고객불만 수정]                         [×]
불만일 [YYYY-MM-DD]    사이트 [TPI ▼]
채널   [전화 ▼]        중요도 [높음 ▼]
제목   [                                             ]
내용   [                                             ]
       [                 여러 줄 입력                ]
연결 Q&A [기존 연결 확인 / 선택 / 해제]
작성일 … / 최종 수정일 …
                                      [취소] [저장]
```

모바일은 필터 줄바꿈과 목록 영역 가로 스크롤을 사용하고, 본문 전체가 화면 밖으로 밀리지 않게 한다. 상세에서 긴 내용과 빈 값을 구분하여 표시한다.

## 2. Implementation (구현 순서)

1. 현재 main 독립 브랜치에서 기존 complaint API·대시보드 집계·메뉴 가시성 규칙을 재확인한다.
2. 기존 `yearMonth` 배열 응답 호환을 유지하고, 페이지용 검색 endpoint(예: `GET /acm/dsh/complaints/search`)에 검증된 기간/사이트/채널/중요도/검색/페이지 인자를 추가한다. 날짜 컬럼의 범위 비교를 사용한다. 기본 페이지 크기 20, 최대 100. 단건 상세 GET을 추가한다.
3. PUT 수정 DTO에 날짜·최종 수정 시각을 추가하고 입력 해제 처리 및 동시 수정 충돌을 구현한다. 조회·수정 조건 모두 ent_id/비삭제 조건을 사용한다. 연결 Q&A의 테넌트와 유효성을 확인한다. 기존 작성자를 보존한다.
4. 날짜·사이트 변경 시 전후 날짜 통계를 재계산한다. 저장/집계 실패가 성공으로 표시되거나 재시도 시 중복 등록으로 이어지지 않도록 오류·트랜잭션 경계를 검토한다.
5. 공통 등록·수정 폼에 textarea/길이 제한/오류·저장중 표시와 기존 값 초기화를 적용한다. Q&A는 UUID를 사용자가 직접 입력하게 하는 기존 UI 대신 조회/선택/해제 동작을 제공한다.
6. `/admin/complaints` 목록과 상세·편집 연결, 대시보드 목록 바로가기, 4개 언어를 추가한다. 기간·사이트·페이지는 URL과 동기화하고 조건 변경 시 첫 페이지로 돌아간다.
7. AppShell NAV 및 FE/BE 메뉴 키와 메뉴 설정 UI를 함께 갱신한다. 기존 테넌트의 저장된 메뉴 순서가 있어도 최초 삽입은 수업통계 바로 아래가 되도록 순서 병합을 검증한다. 기존 표시/숨김 설정과 다른 메뉴 순서는 보존한다.
8. 목록 필터·정렬·페이징, 상세, 빈 내용 지우기, 날짜/사이트 변경의 KPI 대사, Q&A 해제·타 테넌트 참조 거부, 동시 수정 충돌, 테넌트 격리, 등록 후 목록 표시를 테스트한다. 데스크톱/모바일과 메뉴 위치를 확인하고 빌드 후 보고서를 작성한다.
