# Site Marketing Input (사이트별 마케팅 입력)

## 1. Changes (변경)
- 일별 입력창에 TPI/TA/SC GA 원본, 추가 방문자 입력, 최종 방문자, 사용광고비, 효과를 함께 표시한다.
- 광고매체/광고비 행 추가·수정·삭제, 사이트별 소계 및 공통 비용 포함 통합 비용을 지원한다.
- 사이트 카드·일별 표·CSV에 사용광고비 명칭을 적용한다. 효과는 기존 상담+지원 산식을 유지한다.
- 보정 저장 날짜만 GA+보정 방식으로 전환한다. 과거 수기 방문자와 비용을 일괄 변환하지 않는다. GA 미수집을 0으로 만들지 않는다.
- 일별·월별·기간 요약·사이트 비교 조회에 동일 resolver를 적용한다. GA 재수집 후에도 보정은 유지된다.
- 마케팅 저장은 하나의 트랜잭션으로 처리하며 revision 충돌, 테넌트/날짜/사이트별 광고 행 소유권, 음수/소수/초과값을 검증한다. 변경 전후 이력을 저장한다.
- CS·수업은 별도 저장 버튼으로 구분하며 생략 필드를 유지한다. 날짜/사이트 변경과 닫기 시 미저장 입력을 보호한다.

## 2. Validation (검증)
- 백엔드 및 프론트엔드 빌드 성공.
- 기존 단위 테스트: 77 suites / 611 tests 통과.
- PostgreSQL 마케팅 통합 테스트: 12개 통과. 기존값 보존, 사이트 합계, GA 갱신, 보정 해제, 미수집/0, 비용 단독 수정, 광고 행 수정·삭제, revision, 테넌트/행 소유권, 레거시 쓰기 보호, 음수 공통 차액 거절, 날짜/DTO 검증 포함.
- 신규 API GET/PATCH는 기존 ACM JWT 및 테넌트 가드를 사용한다.
- 기존 프론트 번들 크기 경고는 유지된다.

## 3. Deployment (배포)
- SQL `1019-dsh-marketing-adjustments.sql` 선적용 필요. 기존 표/값 변경 없는 추가 테이블 방식이다.
- 스테이징 → 운영 파이프라인 및 읽기 전용 화면 확인 예정.
- 롤백 시 새 테이블/이력은 보존한다. 구버전 UI는 신규 보정/명세를 표시하지 않으므로 되돌리기 전에 영향 날짜를 확인한다.

## 4. Limits (제한)
- 기존 통합 비용이 사이트 합보다 작으면 공통 비용을 추정하지 않고 전환을 차단한다. 기존 비용 확인 후 정리가 필요하다.
- 운영 데이터에 시험용 보정/광고비를 저장하지 않는다. 실제 저장 검증은 격리 PostgreSQL에서 수행한다.
