IV.Integration Flow— 데이터·이벤트 흐름

TRINITY ACADEMY

학원 운영·결제 레이어
  • OWNProgram, Class, Session, Enrollment, Attendance
  • OWNParent, Student (TPI), Consultation, Visit
  • OWNMAP Passage / Item / TestSet / Score 이력
  • OWNTimetable = Class × Session 파생 뷰
  • OWNPayment · Refund · Invoice (Trinity Pay)
  • CACHEteachers.cached_profile ← AMA

BRIDGE · 연동 레이어

Event · Webhook · API
  • INPOST /webhooks/ama (HMAC) → RabbitMQ
  • OUTTrinity → AMA REST (Client search / fetch)
  • OUTenrollment.created / map.graded → AmoebaTalk
  • INPG Webhook (payment.succeeded / .failed)
  • BATCH02:00 KST drift-guard polling (7-day)
  • AUTHService Token + mTLS (내부망)

AMA & PG

마스터 · 메시지 · 결제
  • MASTERAMA Client(거래처) = 교사 원본
  • EVENTAMA: client.updated / .deactivated
  • APIAMA: GET /clients, /clients/{id}
  • MSGAmoebaTalk Send API
  • PAYTrinity → PG 직결 (AMA 경유 X)
  • LIMITAMA는 결제·정산에 관여하지 않음
◀ Trinity가 AMA·PG를 호출 (참조/결제)　　|　　AMA·PG가 Trinity로 이벤트 푸시 ▶

VIII.Guiding Principles— 핵심 원칙

Principle I
Trinity Owns Operations & Payment

학원 업무·결제·MAP·시간표의 쓰기 주체는 Trinity. AMA 및 외부 서비스는 이 도메인에 쓰기 권한을 갖지 않는다. 결제는 Trinity Pay 모듈 → 외부 PG 직결.

Principle II
AMA as Master for Teachers

교사(거래처) 마스터는 AMA가 유일한 원본. Trinity는 ama_client_id로 참조·cached_profile로 캐시만 유지. AMA Client 원본 수정은 금지.

Principle III
Event-driven · Resilient Bridge

상태 변경은 RabbitMQ 이벤트로 분리하여 장애를 격리. Webhook 실패에 대비해 일일 02:00 KST Polling으로 drift 보정. 결제 Webhook은 멱등성 키로 중복 방지.
