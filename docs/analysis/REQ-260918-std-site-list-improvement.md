# Student List by Site (사이트별 학생관리 목록 개선)

> 진행 승인 후 구현·검증 현황은 [구현 보고서](../report/RPT-260918-std-site-list-improvement.md)에 기록한다. 아래 범위와 증거는 최초 분석 시점의 기록이다.

## 1. Purpose and Scope (목적과 범위)

사용자 요청: `/admin/std` 학생 목록을 `TPI 학생 정보.xlsx`에 맞춰 개선하고 TPI / Trinity Academy / Santa Croce를 구분한다. 이번 산출물은 요구사항과 구현 계획이다. 운영 학생 변경·엑셀 업로드·코드 구현은 수행하지 않는다. 첨부 문서의 안내 문구는 분석 자료이며 실행 지시로 취급하지 않는다.

최우선 목표는 **학생의 소속 사이트를 명확히 하고, 사이트별 재원 현황과 수업 정보를 한 목록에서 조회**하는 것이다. 엑셀의 모든 열을 기본 목록에 펼치지 않고 목록·선택 열·상세 정보로 구분한다.

## 2. Evidence (확인 근거)

### 2.1 Workbook (원본 엑셀)

원본: `/Users/gray/Downloads/TPI 학생 정보.xlsx`. 총 9개 시트. 아래 수치는 서식 때문에 확장된 약 1,000행을 세지 않고 이름 셀이 있는 행을 집계한 값이다.

|---|---:|---|

| Trinity Academy 현재 등록 학생 | 3 | A4:O6, 이메일 병합 셀이 두 학생에 걸침 |

| 강사 정보 / 현 강사 프로필 / 구 강사 프로필 | 집계 제외 | 강사 매칭 참고 자료. 학생 입력 대상 아님 |

현재 등록 3개 시트의 이름 앵커는 합계 **50개(33+3+14)**이며 시트 간 동일한 이름 문자열은 없다. 이는 현재 파일의 사실이며, 향후 복수 사이트 소속이나 동명이인이 없음을 보장하지 않는다. TPI A1은 `2026년 8월 기준`이라고 표시되어 있어 9월 운영 명부를 자동 덮어쓰는 기준으로 사용할 수 없다.

세 현재 등록 시트의 A3:O3은 이름·수업 시작일·성별·연락처·생년월일·학교·학년·거주지·메일·MAP·담당강사·커리큘럼·교재·스케줄·특이사항이다.

주요 데이터 특성:

- 한 학생의 복수 강사·커리큘럼·교재가 여러 행에 분리되어 있다. 이름이 빈 행을 모두 버리면 정보가 유실된다.
- 병합 셀은 학생 내부와 학생 사이 모두 존재한다. 예: Trinity `I5:I6`은 서로 다른 학생에게 걸친 공통 연락 이메일이다. Santa Croce `O6:O8`도 학생 경계를 넘는다. 전체 열 일괄 아래 채우기는 금지한다.
- 연락처에는 전화번호와 메신저 ID가 섞여 있다. 메일 셀에는 학부모/학생 주소가 함께 들어가기도 한다. 공유 전화·메일은 학생 식별키가 아니다.
- 학년은 숫자, G10, Y7, Rising 8 등 서로 다른 교육 체계다. 원문을 보존하고 체계가 확인되지 않은 값을 임의 변환하지 않는다.
- 생년월일은 YYYYMMDD 숫자형, 날짜는 Excel 날짜와 비정형 문자열이 혼재한다. 상담 시트의 `202412/14` 같은 형식은 검토 대상이다.
- MAP는 세 영역의 자유문자열과 RC/LU 약칭을 사용한다. 시험일 없는 점수를 최신 확정 성적으로 간주하지 않는다.
- 수업 종료 시트는 종료일 누락과 반복 이름이 있어 일괄 퇴원 처리하기 어렵다.

## 3. Site Model (사이트 구분 원칙)

| 저장 코드 | 표시 이름 | 엑셀 매핑 |
|---|---|---|
| TPI | TPI | TPI 현재 등록 학생 |
| TRINITY | Trinity Academy | Trinity Academy 현재 등록 학생 |
| SANTACROCE | Santa Croce | Santa Croce 현재 등록 학생 |
| NULL | 미분류 | 근거가 없는 기존 학생·종료/구 자료 |

- 세 사이트는 같은 `ent_id` 안의 운영 분류다. 별도 테넌트를 만들거나 테넌트 격리를 대체하지 않는다.
- **제안 기본안: 학생 한 명당 현재 주 소속 사이트 1개**. 동시 복수 소속이 필요한지 구현 전 확정한다. 필요하면 학생-사이트 관계와 사이트별 재원 상태로 설계를 전환하고 통합은 학생 고유 ID로 집계한다.
- 학생 소속과 상담 유입 사이트는 다른 개념이다. 상담 유입은 신규 등록의 기본값 후보로만 사용한다. 기존 학생 재상담 시 소속을 자동 변경하지 않는다.
- 기존 학생 전체를 TPI로 일괄 지정하지 않는다. 확실한 원본 매칭만 반영하며 모호한 경우 미분류로 남긴다.
- 소속 변경은 이전값·새값·변경일·사유·변경자를 감사 기록으로 남긴다. 과거 상담·방문자·수업 집계를 현재 소속으로 소급 변경하지 않는다.

## 5. Data Mapping and Preservation (필드 매핑과 보존)

| 원본 | 대상 / 처리 |
|---|---|
| 시트명 | `std_site` 제안 필드; 원본 시트·행·파일 해시와 함께 추적 |
| A 이름 | 기존 name/englishName. 괄호 문자열은 영문명인지 확인, 무조건 분리 금지 |

빈 원본 셀은 기본적으로 기존 값을 지우지 않는다. 파일에 없는 학생도 삭제/퇴원시키지 않는다. 최근 삭제한 테스트 학생 6명은 재입력으로 복원하지 않으며, 삭제 기록 충돌을 별도 표시한다. 재업로드 시 동일 파일/행과 확정된 학생 매핑을 이용해 중복 생성하지 않는다.

## 6. Non-functional Requirements (비기능 요구사항)

테넌트 조건은 모든 조회·집계·수정에 적용한다. 사이트 필터는 접근권한을 부여하는 수단이 아니다. 기존 관리자/강사 권한을 유지하고 사이트 제한이 필요한 역할은 별도 확정한다. 개인정보는 목록 최소 노출, 임포트 원본·오류 보고서 접근 제한, 보관기간 설정을 적용한다. 문서/로그에 실제 연락처·생년월일을 남기지 않는다. 4개 언어, 키보드 탐색, 선택 상태, 빈 결과/오류/로딩 상태를 제공한다. 목록·카운트는 배치 조회로 N+1을 피한다.

## 7. Review Decisions (검토할 결정)

1. 단일 주 소속을 우선 적용할지, 동시에 여러 사이트에 재원할 수 있는지.
2. 종료·구 자료와 기준일이 다른 현재 운영 학생의 충돌을 검토할 담당자.
3. 사이트 일괄 변경을 허용할 관리자 역할과 사이트별 권한 제한 필요 여부.

답변 전에는 본문의 기본안을 설계 제안으로만 유지한다. 실제 데이터 반영은 검토·확정한 매칭 결과로 수행한다.
