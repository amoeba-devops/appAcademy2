# 요구사항 분석서 — 수업일정 삭제 사유 · 삭제목록 보기 · 수정 히스토리

> **One-liner**: 운영자(AMA 유저/학원 관리자)가 수업일정을 **사유와 함께 soft-delete** 하고, 삭제된 일정은
> 캘린더에서 숨기되 **"삭제한 수업일정 보기"** 로 열람하며, **일정 수정 시 수정 사유를 남기고 수정 히스토리를
> 조회**할 수 있게 한다.

---

## 1. Overview (개요)

### 1.1 배경 / 현행(As-is)
- `/admin/cal` 수업일정은 이미 **soft-delete** 되어 있다 — `remove()` 가 `deleted_at` 을 채우고([cal-event.service.ts:519-538](../../backend/src/modules/acm-cal/application/cal-event.service.ts#L519)), 목록 조회는 `deleted_at IS NULL` 로 **캘린더에서 자동 숨김**.
- 그러나 **① 삭제 사유가 없다, ② 삭제된 일정을 다시 볼 UI/API 가 없다, ③ 수정 시 사유·히스토리가 없다.**
- 권한(현행 `assertCanMutate`): `ADMIN` 은 전체, 그 외는 **본인 작성(owner) + MANUAL 소스**만 수정/삭제 가능.

### 1.2 목표(To-be)
1. 삭제 시 **삭제 사유 필수 입력** + 삭제자·삭제시각 기록.
2. 삭제된 일정은 캘린더 미표시(현행 유지) + **"삭제한 수업일정 보기"** 토글로 별도 열람(사유·삭제자·시각 표시).
3. 일정 수정 시 **수정 사유 입력** + **수정 히스토리(누가·언제·사유·변경내용)** 기록·열람.

### 1.3 비목표(Out of scope)
- 삭제 일정 **복원(restore)** — v1 미포함(열람만). 필요 시 후속.
- 필드 단위 diff 시각화(리치 diff) — v1 은 변경 필드 요약 수준.
- 반복 일정(시리즈) 일괄 삭제/수정 이력 — 개별 이벤트 단위로 처리.

## 2. Functional Requirements (기능 요구사항)

### FR-1. 삭제 권한 (Authorization)
- 수업일정 삭제 가능 주체: **AMA 유저/학원 관리자(`ADMIN`)**. (현행처럼 작성자 본인도 허용할지는 **Q-1** 결정.)
- 삭제/수정 모두 테넌트 격리(`OwnEntityGuard`) 유지.

### FR-2. 삭제 사유 입력 (Soft-delete with reason)
- 삭제 시 **삭제 사유(필수, 2~500자)** 를 입력한다. 사유 없이 삭제 불가.
- soft-delete: `deleted_at` + **`evt_delete_reason`** + **`evt_deleted_by`(user)** 기록.
- BODASCHOOL 이벤트는 현행대로 SERVER API `/close` 후 처리(사유 저장은 유지).

### FR-3. 삭제 일정 숨김 + "삭제한 수업일정 보기"
- 삭제된 일정은 캘린더 그리드에 **미표시**(현행 유지).
- `/admin/cal` 상단에 **`삭제한 수업일정 보기`** 토글/버튼. 클릭 시 해당 기간의 **삭제 목록**을 조회한다.
- 삭제 목록 항목: 제목 · 기간 · **삭제 사유 · 삭제자 · 삭제 시각**.
- 목록 API: 기존 list 에 `deletedOnly=true`(또는 `includeDeleted`) 파라미터 추가.

### FR-4. 수정 사유 입력 + 히스토리 기록
- 일정 **수정 저장 시 수정 사유(필수 or 선택 — Q-2)** 를 입력한다.
- 각 수정마다 **수정 히스토리 1건** 생성: `evt_id` · 수정자 · 수정 시각 · 사유 · **변경 요약**(변경된 필드 목록 + 이전/이후 값).
- 히스토리는 **append-only(불변)** — 삭제/수정 불가.

### FR-5. 수정 히스토리 열람
- 일정 상세(수정 모달)에서 **수정 히스토리** 를 시간역순으로 열람한다(수정자·시각·사유·변경내용).

## 4. 데이터 모델 (Data model 초안)

**이벤트 컬럼 추가** (`amb_acm_cal_event`)
- `evt_delete_reason VARCHAR(500)` nullable
- `evt_deleted_by UUID` nullable (삭제자 user_id)

**신규 수정 히스토리 테이블** `amb_acm_cal_event_revision`
| 컬럼 | 설명 |
|---|---|
| `rev_id UUID PK` | |
| `ent_id UUID` | 테넌트 |
| `evt_id UUID` | 대상 이벤트 |
| `rev_editor_user_id UUID` | 수정자 |
| `rev_reason VARCHAR(500)` | 수정 사유 |
| `rev_changes JSONB` | 변경 요약 `[{field, before, after}]` |
| `created_at TIMESTAMPTZ` | 수정 시각 |
- 인덱스: `idx_acm_cal_evt_rev_evt (evt_id, created_at)`

> 삭제 사유는 이벤트 컬럼(단발), 수정 사유/변경은 다건이므로 별도 테이블. (삭제도 revision 에 `DELETE` 종류로 통합 가능 — Q-3.)

## 6. Acceptance criteria

| AC | 시나리오 | 기대 |
|---|---|---|
| AC-1 | 사유 없이 삭제 시도 | 오류, 삭제 안 됨(사유 필수) |
| AC-2 | 사유 입력 후 삭제 | soft-delete + 사유·삭제자·시각 기록, 캘린더에서 사라짐 |
| AC-3 | "삭제한 수업일정 보기" 토글 | 삭제 목록에 사유·삭제자·시각 표시 |
| AC-4 | 일정 수정 저장 | 히스토리 1건 생성(수정자·사유·변경요약) |
| AC-5 | 상세에서 히스토리 열람 | 시간역순, 변경내용 표시 |
| AC-6 | 비인가자 삭제 시도 | 403 |
| AC-7 | i18n | 4 locale 누락 없음 |
